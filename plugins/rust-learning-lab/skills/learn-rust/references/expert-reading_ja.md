# 型から分かることと、まだ分からないこと

[English](expert-reading.md) | 日本語

熟練したRustの読み手が、記号や型から何を読み取るかを深く説明するときに使う。
学習者の目的と一つの関数の宣言から始め、言語の規則から分かること、実装で確かめること、測定が必要なことを分ける。
毎回答えるチェックリストではなく、すべての熟練者が同じように考えるという主張でもない。
見慣れない記法には[記号ガイド](symbol-guide_ja.md)を使う。

## 関数の宣言を、つながった条件として読む

プロジェクトで定義した型 `Record` を使う、次の宣言を考える。

`fn find_record<'a>(records: &'a [Record], key: &str) -> Option<&'a Record>`

「レコードの並びと検索キーを借り、見つかればレコードを借りた参照を返す。その有効期間はレコード側に結び付く」と読む。
そこから導けることと、その限界を一つずつ対応づける。

| 見えている情報 | 呼び出し側が頼れること | それだけでは分からないこと |
|---|---|---|
| `records: &'a [Record]` | 呼び出し側のコレクションを消費せず、スライスを借りる。この共有参照を通して通常のフィールドを書き換えることはできない | 内部可変性による変更、グローバルな副作用、同期処理、関数内のメモリ確保がないか |
| `key: &str` | 文字列スライスを借りるため、呼び出し側の `String` の所有権を渡す必要はない | 比較の規則、正規化の有無、内部で文字列をコピーしているか |
| `Option<…>` | 通常の返却には `Some` と `None` があり、呼び出し側は値がない場合の扱いを選ぶ | 見つからない理由、panicする可能性、必ず終了するか |
| 出力の `&'a Record` | 返す参照は宣言した有効期間の関係を満たす必要があり、独立した検索キーのライフタイムには制約されない | どのレコードを選ぶか、そのスライスの中身を返すと証明できるか。条件を満たす、より長く有効な別の参照も型には合い得る |
| 入出力で共通の `'a` | 結果を使う間、必要な借用の有効性を呼び出し側が保つ | 所有者が自動的に生き続けること、コレクションを破棄しても結果を使えること |

出力のライフタイムは有効性の条件であり、実行時にどこから参照を取り出したかをすべて表す情報ではない。
説明的な関数名は意図の手がかりになるが、要素がその中にあること、順序、一意性、計算量までは証明しない。
[検索の実行例](worked-examples_ja.md#関数の宣言から読み実装で検索方法を確かめる)では、キーを先に破棄しても結果を使えることを確認し、
どの要素を選び、どう探すかは本体を読んで確かめる。

境界を知るには、[入力が二つあるライフタイムの例](worked-examples_ja.md#ライフタイムの関係と実行時に選ぶ値は別の情報)も使える。
引数が `true` でも、宣言のライフタイムの条件を呼び出し側で無視できるわけではない。
コンパイルの失敗は宣言から分かる情報が足りない場合にも起こり、その入力で必ずメモリの問題が起きるという判定とは限らない。

## 式を通して、所有権と許されるアクセスを追う

`value`、`&value`、`&mut value`、`*reference` は、見た目だけが違うのではなく操作が異なる。
`T` を値で渡す場合は、まず `Copy` を確認する。非 `Copy` の値は移動し、`Copy` の値はコピーされる。
`String` の移動は所有権を渡し、文字列のバッファをcloneすることではない。
`clone()` の動作と費用は型によって異なり、`String` と `Rc<T>`・`Arc<T>` では内容が違う。
「cloneは遅い」と一律に判断しない。

`&T` では共有アクセスにより通常の変更が制限されるが、純粋な処理であるとは限らない。
`Cell`・`RefCell`・アトミック型・ロックなど、内部可変性を持つフィールドなら共有参照を通して状態を変えられる場合がある。
`&mut T` では、借り直した参照も含め、借用した対象への排他的なアクセスを考える。「ポインタが世界に一つしかない」とは説明しない。
無関係な状態まで排他的に扱えるわけでもない。[内部可変性の資料](https://doc.rust-lang.org/std/cell/index.html)で確認する。

`*r` は参照先の型と、その周囲の式が何をするかを合わせて読む。`Copy` の値を読む、参照先を借りる、書き換える、
許されない所有権の移動を試みる、といった違いがある。
メソッドの記法が手順を隠している場合は、受け手の型と必要な参照外し・借用を示す。
[再帰的なリストの例](worked-examples_ja.md#再帰型間接参照再帰呼び出しが解く問題は異なる)では、`&List` への照合で参照が束縛され、
`rest.sum()` は次のノードを消費せずに借りる。
Edition 2024では、この暗黙の参照束縛に冗長な `ref`・`ref mut`・`mut` を自由に追加できるわけではない。
まず推論された束縛の型を説明し、古い例との比較には[2024のパターンの規則](rust-2024_ja.md)を使う。

## 誰が型を選び、いつ処理が進むかを読む

| 記法・制約 | 読み取れること | 分けておくべきこと |
|---|---|---|
| `T: Trait`、引数位置の `impl Trait` | 呼び出し側が条件を満たす具体型を渡し、本体は制約で示された操作を使える | 特定のアルゴリズム、性能、副作用のない実装までは保証しない |
| 戻り値位置の `impl Trait` | 実装側がジェネリック引数の具体化ごとに隠された具体型を決め、呼び出し側は公開された制約を通して使う | 同じトレイトを実装しているだけでは、分岐ごとに無関係な型を返せない。`impl` だけでヒープ確保や動的ディスパッチが決まるわけではない |
| `&dyn Trait` / `Box<dyn Trait>` | 動的にメソッドを選ぶトレイトオブジェクトを使う。前者は借用、後者は所有 | `dyn` だけではヒープ確保を意味しない。周囲のポインタ型と生成方法を見る |
| `FnOnce` / `FnMut` / `Fn` | それぞれのトレイトを通した呼び出しは、呼び出せる値自体を消費／可変借用／共有借用する | `FnOnce` はAPIが必ず一回呼ぶという約束ではない。`Fn` も純粋な計算や内部の状態を変えないことを意味しない |
| `Iterator<Item = &'a T>` | 取り出す要素は `'a` の間有効な共有参照 | この制約だけでは順序・有限性・費用は決まらない。`map` など通常の遅延アダプタでは、何が反復を進めるかを確認する |

Edition 2024の戻り値位置の `impl Trait` では、ライフタイムの捕捉も確認する。
`use<…>` がなければ、ライフタイムを含むスコープ内のジェネリックパラメータを暗黙に捕捉するため、
見える位置に `+ 'a` がないだけでは、借りた入力と独立していると判断できない。
`use<'a, T>` のような指定は捕捉を許すパラメータを明示し、この `use` はインポートではない。
通常の参照のライフタイム省略とは分け、関係する場合は[2024の捕捉規則](https://doc.rust-lang.org/edition-guide/rust-2024/rpit-lifetime-capture.html)を確認する。

型に関する名前と値を分けて説明する。`Item = &'a T` は関連型の指定で、`|item| …` はクロージャを呼ぶたびに値を束縛する部分。
`move` はクロージャが周囲の変数を捕捉する方法を変え、実装される呼び出しのトレイトは本体の使い方によって決まる。
所有する値を捕捉しただけで、一度しか呼べなくなったり、別スレッドで動いたりするわけではない。
`.filter(|x| …)` では、イテレータの `Item` と判定処理の宣言を確認してから `*x` を読む。参照が一段増えている場合がある。

参照：[具体型を隠す型](https://doc.rust-lang.org/reference/types/impl-trait.html)、
[トレイトオブジェクト](https://doc.rust-lang.org/reference/types/trait-object.html)、
[`FnOnce`](https://doc.rust-lang.org/std/ops/trait.FnOnce.html)、
[`FnMut`](https://doc.rust-lang.org/std/ops/trait.FnMut.html)、
[`Fn`](https://doc.rust-lang.org/std/ops/trait.Fn.html)。

## 構文の処理・型の検査・実行を分ける

`::<u32>` は型引数を指定し、`'a` は有効期間の関係を記述する。型の番号や寿命の秒数を通常の実行時引数として渡す記法ではない。
式の `?` は実行時の処理の行き先を変え得る。マクロ内の `$value:expr` は、プログラムの実行前に展開される構文を受け取る。
Edition 2024で定義したマクロの `expr` は、最上位のconstブロックやアンダースコア式にも一致する。
以前の照合範囲は `expr_2021` で保てる。構文が一致しても、展開後の型が合うとは限らない。
受け付ける構文や選ばれるマクロの規則が問題になる場合は、[Editionによる違い](https://doc.rust-lang.org/edition-guide/rust-2024/macro-fragment-specifiers.html)を確認する。
[マクロと関数の対比例](worked-examples_ja.md#マクロの展開は構文を扱い関数呼び出しは評価済みの値を受け取る)で、
構文を繰り返すと副作用も繰り返され得る一方、関数の引数の値を何度使っても呼び出し側の引数を再評価しないことを示す。
これらの段階を、単に「記号が何かをする」と一括りにしない。

同様に、型の再帰的な定義、値をたどる処理、値そのものに循環があることを分ける。
`Box` はメモリ配置を有限にする間接参照を用意し、自動的な走査や無制限のスタックを用意するわけではない。
[リストの例](worked-examples_ja.md#再帰型間接参照再帰呼び出しが解く問題は異なる)で、それぞれの役割を示す。
一般的な哲学の主張を、そのまま言語仕様として持ち込まない。

## 型が表すデータと動作の範囲を確かめる

| 見えている型や操作 | 次に確かめること |
|---|---|
| `String`、`&str`、`char`、バイト列 | 数えているのはバイト、Unicodeスカラー値、利用者が一文字と捉えるもののどれか |
| `Eq`、`Ord`、`Hash` | 値の変更後も含め、必要な法則と相互の関係を実装が守っているか |
| `Write` と `Result` | 入力をすべて書いたか。完了はバッファーや永続化について何を意味するか |
| `Pin<P>` | `P` は何を指すか。`Unpin` によって参照先の移動が許されるか |
| 内部で `unsafe` を使う安全なAPI | エラーや破棄も含め、許される安全な操作すべてを成立させる条件は何か |

Rustの[`char`](https://doc.rust-lang.org/std/primitive.char.html)はUnicodeスカラー値であり、
[`String::len`](https://doc.rust-lang.org/std/string/struct.String.html#method.len)はバイト数を返す。
どちらからも表示幅や利用者にとっての一文字をそのまま推定しない。
`Length` のような名前にも、意味を明確にする単位や操作が必要になる。

traitの実装には、コンパイラの検査だけでは確かめられない意味上の条件がある。
たとえば[`Eq`](https://doc.rust-lang.org/std/cmp/trait.Eq.html)は反射律を要求するが、コンパイラはそれを証明しない。
コンパイルできることだけでは、順序・等価性・ハッシュ値の整合は確かめられない。

[`Write::write`](https://doc.rust-lang.org/std/io/trait.Write.html)は、要求したバイト数より少なく書いて成功する場合がある。
`write_all` は必要な反復を行うが、先行する書き込みが成功した後にエラーになることもある。
任意のwriterの成功や `flush` を、永続化の完了とは一律に解釈しない。具体的なwriterと、ファイルなら
[`sync_all`](https://doc.rust-lang.org/std/fs/struct.File.html#method.sync_all)が説明する範囲を確認する。

[`Pin`](https://doc.rust-lang.org/std/pin/index.html)は、pinされたAPIを通じた参照先の移動を制約する。
ポインターを包む値自体の移動とは別であり、一般的な不変性や同期の仕組みでもない。
安全なAPIの内部で `unsafe` を使う場合、コンパイルや少数の例の成功だけでは、その安全性を支える条件を証明できない。

プロセス・保存先・時間をまたぐ失敗には[システムの境界](systems-thinking_ja.md)を、
データ表現の選択や変更の確認には[判断と検証を学ぶ](engineering-practice_ja.md)を使う。
どの型にもこの表全体を説明せず、関係する問いを選ぶ。

## 読み取ったことを、確かめられる予測へつなげる

深く説明するときは判断の流れを見せる。根拠となる記号を指し、推論した型や可能な操作を述べ、
観察できる結果を一つ予測し、まだ分からない点を確かめるために何を調べるかを示す。
元の値を引き続き使えるか、どの所有者を保持する必要があるか、失敗時に抜けるのは関数かクロージャか、
副作用のある式を何回実行するか、といった予測が使える。
答えを先に示し、自力での予測や小さな変更は、練習の依頼がなければ任意にする。

トレイト・型の別名・マクロ・暗黙の変換が判断を左右する場合は、実際の定義を読む。
一つの例が成功しても、その抽象化のすべての性質が確かめられたことにはならない。
型や実装の確認で決まらない性能は、プロファイリングや測定で確かめる。
コンパイルが通ること、説明を受けたこと、自力で理解を示せたことを同じ成果として扱わない。
