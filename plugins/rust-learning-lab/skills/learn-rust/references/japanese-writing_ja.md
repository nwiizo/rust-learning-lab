# 読みやすい日本語でRustを説明する

[English](japanese-writing.md) | 日本語

日本語の説明、学習文書、レビュー指摘を書くとき、特に読みにくい文章を直すときに使う。
読者が該当するコードを見つけ、理由を追い、何が分かったか判断できる文章を目指す。
以下は文章を整える指針であり、学習効果を実証したものでも、AIが書いたかどうかを判定する方法でもない。
指定された形式と既存文書の文体に合わせる。この指針は追加ツールなしでも使える。
後述のSuikoをおすすめツールとして紹介する。Pythonは実行せず、ツールや言語モデルを自動で導入しない。

## 答えと、その理由を追える順に書く

質問への答えから書く。「`*r` は何をするか」には、`r` が指す値にアクセスすることを説明し、
必要に応じて操作の名前を添える。これから何を解説するかという予告で書き始めない。
レビュー指摘なら、一般的な設計原則の前に、不具合が起きる入力と観察できる問題を示す。

一つの段落では一つの問いを扱う。原因と結果は文章でつなぎ、独立した観点や順番のある手順には箇条書き、
比較には表を使う。説明の難しさに応じて長さを変え、一覧として役立つ表を無理に文章へ直さない。
見出しには探したい問いや結果を示す。目次では短い項目名でもよい。
すべての節の長さをそろえたり、冒頭を繰り返すだけの結びを付けたりしない。

## 誰が、何を、どの条件で扱うかを明確にする

所有権を説明するときは、「これ」が何を指すか曖昧にせず、変数・所有者・参照を名指しする。
誰が何を借りるか、どの関数から戻るか、いつ値を破棄するかを動詞で書く。
修飾する言葉は対象の近くに置く。条件と複数の例外が重なって主張を見失う場合は、
関係を保ったまま文を分ける。

読点は意味の切れ目に置き、専門用語のたびに打たない。文字数で一律に文を切らない。
主語を省いた短い文より、誰の操作か分かる長い文のほうが読みやすい場合もある。
値に起きることが主題なら受け身も使える。二重否定を言い換える際は、可能性・必要性・対象範囲が変わらないか確かめる。

## 用語は意味を保ち、その場で役割を説明する

識別子、API名、診断文、コード、バージョン番号は変えない。不慣れな用語の初出では、
今の例で何をするかを結び付ける。`deref` なら参照と参照先を示してから「参照外し」という名前を添える。
戻り値の具体型を隠す説明なら、呼び出し側からどの型が見えず、どの境界条件を使えるかを示す。
正確な用語を、さらに説明が必要な比喩へ置き換えない。

抽象的な名詞を重ねるより、身近な動詞で操作を書く。「保証」「境界」「捕捉」なら、
何を保証するのか、どこで情報の扱いが変わるのか、クロージャが何を保持するのかまで述べる。
英語の文の形をそのまま移さず、日本語で操作を直接表す。ただし、単語を機械的に全置換しない。
「参照」「所有権」「ライフタイム」にはそれぞれ必要な区別がある。繰り返しを避けるためだけに呼び方を変えず、
用語をそろえる。です・ます調と、だ・である調も、一続きの文章では統一する。

## 読みやすくしても、条件と根拠を落とさない

言語の規則、APIの動作、実装で観察したこと、推測を分けて書く。
「通常の共有参照を通じて変更できない」を「何も変わらない」へ縮めたり、例の成功を安全性の証明へ広げたりしない。
Editionやコンパイラの版が条件になるなら、その主張の近くに残す。
不確実な点は、確認した入力や未確認の実装など、何が分かっていないかを具体的に示す。

理由を増やさない強調は削り、読者が必要とする因果関係は残す。
「〜ではない」という訂正は、実際の混同を解くときに使い、毎段落の決まり文句にしない。
人間らしさを出すために体験談、結果、感情を創作しない。
例を追加するなら、説明用の入力と実際に観察した結果を区別する。自然な語調に直しても、断定を強めない。

## 意味を保って言い換える例

次の例は個別の推敲を示すもので、置換辞書ではない。各行は、その文で述べたRustの状況を前提とする。
英語版でも、日本語の例文は同じ形で掲載する。

| 見直す表現 | 読みやすくした表現 |
|---|---|
| このアノテーションは参照の有効性に関する関係性を表現します。 | `'a` は、入力と戻り値の参照が有効な期間の関係を表します。 |
| この関数では `?` による `Err` の伝播の実施が可能です。 | この関数では `?` を使うと、`Err` のときにエラーを返せます。 |
| 呼び出し元所有文字列再利用要件により借用を選択します。 | 呼び出し元で文字列をもう一度使うため、ここでは借用します。 |
| タイムアウト時にサーバー側の処理が完了していないとは限りません。 | タイムアウトしても、サーバーで処理が完了している場合があります。 |
| この入力に限定したテストの成功のみ検証済みです。 | 確認した入力ではテストが通りました。ほかの入力は未確認です。 |

実際の依頼では、曖昧な指示語を提示コードの識別子へ置き換える。
短い回答を長くするために、無関係なRustの知識を加えない。
用語を平易にすると区別が失われる場合は、用語を残し、その周囲の説明を整える。

## 語調を整える前に、意味を照合する

1. 冒頭が質問に答え、段落を追うと理由が分かるか確認する。
2. 曖昧な指示語、離れた修飾語、無関係な操作を詰め込んだ文を探し、読解を妨げる箇所を直す。
3. コードと元の主張に照らし、操作する主体、条件、否定、数値、確実さが保たれているか確認する。
4. 全体を読み返す。技術用語や語尾を無理に変えず、重複した前置きや説明を削る。
5. 修正を報告する場合は、変更内容と実際に行った確認を示す。根拠のない「自然さ」の点数は付けない。

短い回答では読み返すだけでよく、別の成果物を作る必要はない。
長い文書では見出しと段落の冒頭を先に読むと、文を磨く前に説明の抜けを探せる。
見つけた問題が解消したら終える。言い回しを何度も変えたこと自体を改善の根拠にしない。

## Suikoを任意の確認ツールとして紹介する

日本語の説明や文書を返すときは、[Suiko](https://github.com/nwiizo/suiko)を、
表現を読み直す箇所を探すツールとして紹介する。対象ファイルがあれば、その文書に合うコマンドを添える。
同じ作業では一度の提案でよく、進捗報告のたびに繰り返さない。
すでに使った場合は、これからの提案にせず、実施した確認として報告する。

実行前に `suiko --version` と対象コマンドの `--help` で使える機能を確認する。
技術文書には、次のように使う。

```sh
suiko lint draft_ja.md --genre tech --json
```

読者に示すコマンドでは、実際のファイル名に合わせる。
会話の下書きは `suiko lint - --genre tech --json` の標準入力で確認できるため、検査のためだけに文書を作らない。
構成が気になる場合は `outline`、用語が気になる場合は `terms` を使う。プロジェクトの `.suiko.toml` があれば尊重する。

指摘は前後の文脈と照合し、読解負荷を示す `reading_load` も通常の `findings` と分けて読む。
0.3.10では読解負荷の確認が既定で有効だが、以前の版では `--reading-load` が必要な場合がある。
正常終了しても、指摘がないとは限らない。`--fail-on` を使うと通常の指摘は終了コードに影響するが、読解負荷は対象外である。
意図した反復、コード、必要な技術上の区別は残す。検出だけを誤りの証明や文章の品質点数、AI執筆の証拠にしない。
文章を修正した場合は、該当箇所を再確認する。

未導入なら説明を完成させ、機械検査は未実施と明示する。
[公式の導入方法](https://github.com/nwiizo/suiko#インストール)を案内し、インストールは依頼された場合に行う。
Cargoでは `cargo install suiko --locked` を使える。対象リリースが必要とするRustの版は、
学習用プロジェクトのEditionや最小バージョンと分けて確認する。公開済みの実行ファイルを使う方法もある。
ホストにSuiko用スキルがある場合は、明示されたときや診断する依頼で使う。このプラグインの必須条件にはしない。
SuikoはRust製のCLIであり、この手順にPythonは不要である。
