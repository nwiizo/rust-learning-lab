# Rust 2024 Edition

English | [日本語](rust-2024_ja.md)

Read only for Rust 2024, edition migration, or questions where editions change diagnostics or behavior.
Use the relevant section rather than teaching every edition change at once.

## Establish the context

- **Edition and toolchain differ.** Rust 2024 stabilized in Rust 1.85.0. `edition = "2024"` selects syntax and some
  semantics per crate; `rustc 1.xx` identifies the compiler and standard library version.
- **Editions are per crate.** Crates using different editions can interoperate in one dependency graph; dependencies
  do not all need to migrate together.
- **Check `Cargo.toml`.** Read `[package].edition`. Omission means 2015 for backward compatibility.
  For `edition.workspace = true`, inspect the root `[workspace.package]`. `cargo new` explicitly writes the latest stable edition.
- **`rust-version` is separate.** It states the minimum supported toolchain. Rust 2024 requires at least 1.85,
  but actual features and dependencies may impose a higher minimum.

Not everything stabilized in Rust 1.85 is exclusive to the 2024 edition. Separate the effects of changing editions
from those of updating a toolchain.

For example, `use<..>` precise capture became available in Rust 1.82 across editions; the implicit capture
default changed in 2024. Let chains require **both Rust 1.88 or later and edition 2024**. An example advertised
as “2024” therefore does not necessarily run on 1.85. Check the feature's stabilization version separately.

For Rust 1.88 or later, this chain uses the binding in the following condition:

```rust,edition2024
let candidate = Some(4);
let accepted = if let Some(value) = candidate && value > 0 {
    value
} else {
    0
};
assert_eq!(accepted, 4);
```

An earlier failed condition skips the remaining conditions. This feature concerns `if`/`while`
conditions joined with `&&`; it does not make `let` a general boolean expression or allow `||` chains.

## New projects

Specify the edition to create a reproducible Rust 2024 learning project.

```bash
cargo new --edition 2024 hello-rust
cd hello-rust
cargo run
```

Because `cargo new` defaults to the latest stable edition, use `--edition 2024` when an example should remain tied to it.
Explain that `cargo new` creates the project, `edition = "2024"` in the generated manifest selects the edition,
and `cargo run` builds and runs it. Use another edition, such as `--edition 2021`, for a concrete reason such as reproducing older material.

## Migrating an existing project

For an implementation request to migrate, inspect Git status and current test results first. Do not execute migration
commands for an explanation-only request. Follow the official guide, separating necessary dependency updates from edition work.

```text
Inspect dependencies and existing behavior
↓
cargo fix --edition
↓
Change Cargo.toml to edition = "2024"
↓
cargo build / cargo test
↓
cargo fmt
```

- Update dependencies only after identifying the target and reason. `cargo update` can change `Cargo.lock`;
  do not assume a blanket update is necessary, and inspect dependency changes separately from edition changes.
- Run `cargo fix --edition` before changing the manifest's edition. It enables compatibility lints and applies
  fixes intended to preserve existing behavior where possible.
- `cargo fix --edition` prepares the next edition only. From 2015 or 2018, migrate and verify one edition at a time until 2024.
- Disabled features and other platforms' `cfg` branches are not covered by a normal run. Use options such as
  `--all-features` or `--target` when appropriate and describe coverage.
- Non-automatic warnings, doctests, code generation, macros, and FFI require manual attention.
- Do not accept automatically inserted `unsafe` blocks or an `if let` rewritten to `match` solely because it compiles;
  check safety conditions and destruction timing.
- Inspect the final diff and tests, distinguishing edition changes from dependency updates and formatting.

## Changes likely to affect beginner explanations

| Area | Rust 2024 change | What to explain |
|---|---|---|
| Match ergonomics | `mut`, `ref`, `ref mut`, and reference patterns are restricted after implicitly matching through references | Separate the pattern, matched value, and binding type. Remove redundant `ref` first; make reference patterns fully explicit if needed |
| `if let` temporaries | Scrutinee temporaries are dropped before entering `else` | Trace when lock guards or `RefCell` borrows end; consider `match` if the old lifetime is needed |
| Tail-expression temporaries | They can be dropped before local variables rather than extended outward | For errors such as E0597, introduce a local binding and show referent and temporary drop order |
| Return-position `impl Trait` | Without `use<..>`, in-scope generic parameters are implicitly captured, notably lifetimes | Distinguish argument-position `impl Trait`. Explain what the return value may borrow before introducing precise captures such as `use<'a, T>` |
| `gen` | Reserved for future `gen` blocks | Rename an existing identifier or use raw identifier `r#gen` when migration compatibility requires it |
| `Box<[T]>::into_iter()` | In 2024 it yields owned elements; the method call in older editions yields references | Inspect receiver and item types. `into_iter()` takes its receiver by value, but that receiver may itself be a reference; item ownership is not always transferred |
| Prelude | Adds `Future` and `IntoFuture` | Use fully qualified syntax to identify the trait if method names become ambiguous |

## Reading the same code under two editions

These contrasts use an edition on each Rust fence. `rustdoc --test --edition 2024` respects those overrides:
the 2021 examples use the same compiler with different edition rules. This isolates edition differences;
it does not test the minimum supported compiler. `compile_fail` marks intentional rejection.

### Patterns: reconstruct the binding type

Start with a pattern that works in both editions:

```rust,edition2024
let [value] = &[42];
// value: &i32
let _: &i32 = value;
```

The array pattern encounters a reference to an array. Matching through that reference changes the default
binding mode from moving/copying to borrowing, so `value` is `&i32` without an explicit `ref`.

```rust,edition2021
let [ref value] = &[42];
let _: &i32 = value;
```

```compile_fail,edition2024
let [ref value] = &[42];
```

The 2024 restriction concerns **where** explicit modifiers appear, not a ban on `ref`.
When needed, make the reference prefix explicit:

```rust,edition2024
let &[ref value] = &[42];
let _: &i32 = value;
let &[mut number] = &[42];
number += 1;
assert_eq!(number, 43);
```

Here `&` in the pattern matches the reference layer explicitly; it does not create a borrow like `&` in
an expression. `ref value` then borrows the element. `mut number` binds a mutable local `i32`, copied
from the element; it does not make the original array mutable. In 2024, `mut`, `ref`, and `ref mut`
require the default binding mode to be move; reference patterns cannot follow an implicitly borrowed
prefix either. For an ordinary borrowed match, prefer the first form and infer the bindings visibly.

### Opaque return types: possible borrowing versus actual contents

Consider a function that reads a slice's length and returns a range containing only two integers.
The body retains no reference to the slice:

```rust,edition2021
fn positions(items: &[u8]) -> impl Iterator<Item = usize> {
    0..items.len()
}
let items = vec![10, 20];
let positions = positions(&items);
drop(items);
assert_eq!(positions.collect::<Vec<_>>(), [0, 1]);
```

```compile_fail,edition2024,E0505
fn positions(items: &[u8]) -> impl Iterator<Item = usize> {
    0..items.len()
}
let items = vec![10, 20];
let positions = positions(&items);
drop(items);
assert_eq!(positions.collect::<Vec<_>>(), [0, 1]);
```

In 2024 the opaque return type implicitly captures the input lifetime. Callers must allow for a
return value that borrows `items`, even though this body does not. Make independence explicit when
it is an intended property of the API:

```rust,edition2024
fn positions(items: &[u8]) -> impl Iterator<Item = usize> + use<> {
    0..items.len()
}
let items = vec![10, 20];
let positions = positions(&items);
drop(items);
assert_eq!(positions.collect::<Vec<_>>(), [0, 1]);
```

`use<>` is a capture bound, not an import or a runtime operation. It permits no generic parameters
to be captured here. `use<'a, T>` permits the listed parameters; `+ 'a` instead requires the hidden
type to outlive `'a`. Capturing `'a` and outliving `'a` are different statements.
Capturing a type parameter `T` can retain lifetime dependencies contained in that type too.
Do not present `use<>` as a universal repair: a body returning `items.iter()` really borrows the input.

Current precise-capture rules require all in-scope type and const parameters to appear in the list,
and lifetimes used in other return bounds must appear too. An argument written as `impl Trait`
introduces an anonymous type parameter: give it a name such as `T: Trait` before using a capture list.
Check the [precise-capture restrictions](https://doc.rust-lang.org/reference/types/impl-trait.html#precise-capturing)
for a generic API rather than extrapolating from the empty list above.

The 2021 comparison above is for a free function. Before 2024, capture rules already differed for
trait methods and `async fn`. Do not generalize it to every `impl Trait`. These rules also differ from
ordinary reference-return lifetime elision and from a closure's `move` captures.

### Temporaries: dropping a guard changes what can happen next

A temporary is still a value with a destruction point. A `RefCell` borrow guard keeps a runtime
borrow active until it is dropped. Use `try_borrow_mut()` here to observe that point without panicking
or blocking on a lock:

```rust,edition2021
use std::cell::RefCell;
let slot = RefCell::new(None::<u32>);
if let Some(_) = *slot.borrow() {
    unreachable!();
} else {
    assert!(slot.try_borrow_mut().is_err());
};
```

```rust,edition2024
use std::cell::RefCell;
let slot = RefCell::new(None::<u32>);
if let Some(_) = *slot.borrow() {
    unreachable!();
} else {
    assert!(slot.try_borrow_mut().is_ok());
};
```

On the failed match in 2024, the temporary guard is dropped before `else`. In 2021 it remains
alive through `else`. A `match` scrutinee's temporary still lives through the selected arm.
Thus rewriting `if let` as `match` can preserve the branches while changing resource availability.
Automatic migration may choose `match` to preserve old behavior; inspect whether that behavior was wanted.
A named guard lives according to its own scope, so this is not “all borrows end before `else`.”

Tail expressions have a related change. A temporary guard at a block's end is now dropped before
the block's locals, allowing this function:

```compile_fail,edition2021,E0597
use std::cell::RefCell;
fn width() -> usize {
    let label = RefCell::new(String::from("rust"));
    label.borrow().len()
}
assert_eq!(width(), 4);
```

```rust,edition2024
use std::cell::RefCell;
fn width() -> usize {
    let label = RefCell::new(String::from("rust"));
    label.borrow().len()
}
assert_eq!(width(), 4);
```

Shorter temporary scope can also reject previously accepted code: a reference may escape the block
whose temporary supplied its owner:

```rust,edition2021
let width = { &String::from("rust") }.len();
assert_eq!(width, 4);
```

```compile_fail,edition2024,E0716
let width = { &String::from("rust") }.len();
assert_eq!(width, 4);
```

Name the owner outside that block when it must live longer:

```rust,edition2024
let label = String::from("rust");
let width = { &label }.len();
assert_eq!(width, 4);
```

Adding a lifetime annotation cannot keep an owner alive. Track owner, guard/reference, last use,
and drop point separately rather than memorizing “2024 fixes lifetime errors.”

### Macro fragments: identical tokens can select another arm

Macro matching happens before evaluating the resulting expression. These two examples deliberately
assert different arms for the same invocation:

```rust,edition2021
macro_rules! classify {
    ($value:expr) => { "expression" };
    (const $value:expr) => { "const-prefixed" };
}
assert_eq!(classify!(const { 7 }), "const-prefixed");
```

```rust,edition2024
macro_rules! classify {
    ($value:expr) => { "expression" };
    (const $value:expr) => { "const-prefixed" };
}
assert_eq!(classify!(const { 7 }), "expression");
```

The first matching arm wins. In 2024, `expr` accepts a top-level `const` block and `_`; the broader
first arm can intercept tokens previously matched by the second. The relevant edition belongs to
the **macro definition**, not its caller. `expr_2021` preserves the narrower fragment category.
Do not equate accepting `_` as macro input with accepting it in every expanded expression context.

### Method calls: inspect the receiver before predicting ownership

`IntoIterator` for `Box<[T]>` exists across editions on sufficiently recent compilers, but method
resolution for this call changes with the edition:

```rust,edition2021
let names = vec![String::from("Ada")].into_boxed_slice();
for name in names.into_iter() {
    let _: &String = name;
}
assert_eq!(names.len(), 1);
```

```rust,edition2024
let names = vec![String::from("Ada")].into_boxed_slice();
for name in names.into_iter() {
    let _: String = name;
}
// names has been moved.
```

The 2021 method call borrows; the 2024 one consumes the box and yields owned elements. `.iter()`
states borrowed iteration in either edition. `IntoIterator::into_iter(names)` states owned iteration
for this box in either edition. Do not apply the method-call compatibility rule to `for name in names`.

These examples illustrate an expert's reading process: locate the notation, reconstruct the inferred
type or scope, then predict an observable consequence. When a prediction depends on the edition,
record that assumption rather than attributing it to the symbol alone.

## Around `unsafe`

Rust 2024 makes some places requiring safety checks more visible in the syntax. Adding `unsafe` does not make code safe;
it marks a responsibility to check conditions the compiler cannot establish.

- Write extern blocks as `unsafe extern "C" { ... }`. The compiler cannot verify that declared signatures match external implementations.
- Write `no_mangle`, `export_name`, and `link_section` as `#[unsafe(...)]`, checking symbol collisions and linking conditions.
- Even inside an `unsafe fn`, put unsafe operations in small `unsafe { ... }` blocks. `unsafe_op_in_unsafe_fn` warns by default in 2024.
- `std::env::set_var` and `std::env::remove_var` are unsafe in 2024. Read their `Safety` documentation, including restrictions
  on mutating the environment while other threads could run. A block inserted by `cargo fix` is not a finished safety review.
- References to `static mut` are denied by default. Beginners should usually first see an appropriate atomic type,
  `Mutex` / `RwLock`, or `OnceLock` / `LazyLock`, according to the stored value and use.

FFI and global state are advanced topics. Limit explanations to safety conditions directly needed for the question.

Distinguish declaration and use: `unsafe extern` places responsibility for accurate foreign declarations
on their author; an `unsafe fn` places requirements on its caller; an `unsafe { ... }` block is where
the implementation must justify a particular operation. Foreign items are unsafe by default, but an
explicit `safe fn` declaration inside the block can exempt a function whose calls need no extra safety
conditions. The block itself does not make every call unsafe. The syntax is available since Rust 1.82;
2024 requires it for extern blocks.

Environment mutation had platform-dependent safety conditions before this edition too. The edition
changes what callers must write, not whether the underlying operation can race. If only a child
process needs a variable, consider `Command::env` instead of modifying the parent's environment.

## Cargo, macros, and formatting

- `edition = "2024"` normally implies `resolver = "3"`, preferring dependency versions compatible with `rust-version`.
  Explicitly set `[workspace] resolver = "3"` in a virtual workspace when appropriate.
- `macro_rules!`'s `$e:expr` accepts const blocks and `_` expressions too. Use `expr_2021` when preserving the older matching range is necessary.
- Rustfmt has a style edition. `cargo fmt` uses the manifest's edition; when an editor invokes rustfmt directly,
  use `style_edition = "2024"` in `rustfmt.toml` if needed to match CI.

Resolver 3's preference is not proof of minimum-version support. Check the locked dependency graph,
enabled features, targets, and a build/test run on the declared minimum toolchain. Likewise, changing
formatting does not demonstrate that edition-sensitive runtime behavior is preserved.

Other diagnostic details belong in focused explanations: never-type fallback changes from `()` to `!`
when inference otherwise leaves a coercion target unresolved; it does not mean that `!` and `()` were
the same type. Annotate the intended result type where necessary. `gen` and guarded-string token
forms are reservations, not evidence that generator blocks or new string literals are already usable.
