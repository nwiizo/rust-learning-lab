# 判断と検証を学ぶ

[English](engineering-practice.md) | 日本語

AIを使う課題、仕様とテストの学習、既存コードの変更、継続学習に使う。
単純な構文の質問に以下の工程を追加しない。これは学習課題を設計するための実践指針であり、
この組み合わせの教育効果を測定したものではない。

## 何をできるようにするか決める

作るものの成功と、学ぶ人の到達点を分ける。たとえば「数値文字列を合計できる」と
「不正な文字列に出会ったとき `?` がどこから戻るか説明できる」は別の確認項目になる。
構文、実行の追跡、問題の分解、実装、検証のどれにつまずいたかに合わせて課題を選ぶ。

小さな課題なら、次の程度の具体化で十分。既に示された条件は聞き直さない。

- 入力 `["2", "3"]` という文字列の列から `5` を得る。不正な要素ではエラーを返す。
- 入力は読み取るだけで、呼び出し後も使える。空の列は `0` とする。
- 実装できたら、空の列と不正な要素で結果を予測し、その根拠を関数の型と分岐から説明する。

正しい動作に複数の解釈があるときは、判断に必要な点を示す。
未指定のオーバーフロー方針などを、コード生成側の都合で黙って決めない。
短い説明例なら「ここでは小さな値のみ扱う」と範囲を明記する方法もある。

## 見慣れないコードを一つの利用経路から読む

具体的な入力と期待する結果から始め、入口、成功する経路、関係する失敗の経路を一つずつ見つける。
何をするプログラムか分かる前に、すべてのモジュールを読もうとしない。
不明点を減らせるなら、小さな流れを描く。

`入力 → 構文の読み取り → 条件の検証 → ドメインの操作 → 外部への作用 → 結果の通知`

各矢印で、Rustの型、値の所有者、境界を越える失敗の伝わり方を確認する。
たとえば入力の `String` を `&str` として借り、`u32` へ読み取り、数量として検証し、コマンドへ移す流れがある。
表現を変える段階と、業務上の条件を確立する段階を分ける。
`?` から外側の関数・クロージャーへ戻り、その結果をユーザーへどう伝えるか決める呼び出し側まで追う。

| 読みながら確かめること | 見る根拠 |
|---|---|
| このメソッドはどこから来たか | 実際の受け手の型、traitのimport、実装、関係するマクロの展開 |
| なぜこの値の借用が続くか | ライフタイムの関係、保持するフィールド、再借用、後の使用箇所 |
| この失敗は何を意味するか | エラーのvariant、変換、呼び出し元、戻る前に完了した作用 |
| 重複に見える処理がなぜ残っているか | 呼び出し元の違い、互換性、関係するテストと変更履歴 |
| 自分の理解のどこが未確認か | 具体的な不明点と、それを確かめる最小の観察 |

エディタの型表示や定義への移動で暗黙の情報を見えるようにし、対象を絞った診断やテストで仮説を確かめる。
名前や古い図は理解の手掛かりであり、証明ではない。
既存テストは選ばれた期待を記録するもので、古い不具合を保つ場合もある。
観察した動作、意図した動作、なぜそう書いたかという未確認の説明を分ける。

## 呼び出し側の次の判断を明確にする型を選ぶ

曖昧なAPIの奥で実装を高度にするより、呼び出し側の判断に役立つ区別を表す。
許される組み合わせが限られる複数のフラグは `enum` で置き換えられる場合がある。
非公開フィールドと検証付きコンストラクターを持つnewtypeなら、`Quantity` に `u32` より狭い意味を与えられる。
[数量の例](worked-examples_ja.md#検証によって型に狭い意味を与える)では、数値としての読み取りと
条件の検証を分け、その条件がどこで確立するかを示す。
名前を付けて包んだだけで妥当性を保証したとせず、生成・変更・デシリアライズの経路を確認する。

借用する引数と所有する引数は、必要な使い方を表すために選ぶ。
文字列を読むだけのパーサーは `&str` を受け取れ、入力の所有者より長くキューに残るコマンドには、
適切な所有データか別の根拠あるライフタイム設計が必要になる。
cloneやライフタイムパラメーター自体を設計の失敗とせず、その要件から考える。

抽象化は呼び出し側でも評価する。[Cognitive Dimensions](https://www.cl.cam.ac.uk/~afb21/CognitiveDimensions/CDtutorial.pdf)
を参考に、次の問いをRustへ当てはめる。

| APIを読む・変える際の観点 | Rustで確かめること |
|---|---|
| 情報の見つけやすさ | 推論された型と関係する境界条件を一緒に確認できるか |
| 隠れた依存 | 必要なtraitのimport、feature、実行環境の前提を発見できるか |
| 変更の手間 | 検証規則を一つ変えるために、複数の呼び出し元を同時に直す必要があるか |
| 早すぎる判断 | 一つの具体的な操作を試す前に、汎用的な型の構成を設計させていないか |
| 役割の伝わりやすさ | 名前と型で、現在位置と件数、受け付けた処理と完了した処理を区別できるか |

これらはトレードオフを見つける問いであり、品質の点数ではない。多くのジェネリックパラメーターが単純な処理を
見えにくくする場合も、一つの境界で守る規則が繰り返しの検証に埋もれる場合もある。
traitは実際の交換可能性やテスト上の必要に役立つときに使い、関数・クロージャー・enum・具体的なstructで
足りる場合も考える。行数の少なさもジェネリックな境界条件の多さも、万能の品質基準にはならない。

コメントとテストの役割を分ける。テストは失敗条件を実行して示せる。
安全性を説明するコメントは、許されるすべての呼び出しでunsafe操作の前提が満たされる根拠を伝える。
単位、順序、互換性、コードだけから読めない判断の理由を残す。
「明瞭なコードを優先する」を「説明コメントを消す」に変えず、テストをunsafeな抽象化の健全性の証明にもしない。

## 正しさを確かめる力を育てる

期待値は要求や手計算から決める。生成されたコードに合わせて期待値を後付けしない。
コンパイルは型などの制約の確認、テストは選んだ条件での動作の確認であり、目的を満たす保証とは区別する。

テストが学習対象なら、通常の入力に加えて関係する空・境界・失敗の例を選ぶ。
「どんな誤りならこの確認を通ってしまうか」を一つ考える。たとえば常に `0` を返す誤実装を
空入力のテストだけでは検出できない。わざと壊す実験は学習用のコピーで行い、元のファイルを壊さない。
すべての質問にテスト作成や専用ツールを要求しない。

正解を列挙しづらい場合は、入力を変えたときに保たれる関係も使える。
たとえば整数の合計を並べ替えても変えないという性質は、オーバーフローが起きない範囲で確かめる。
浮動小数点の加算や順序に意味がある処理へ無条件に当てはめない。
性質の確認だけでは、常に同じ値を返す実装などを見逃すため、具体的な期待値とも組み合わせる。

判断部分のテストと外部との接続部分のテストを分ける。
純粋な検証関数なら小さな境界値テストができ、DBとの接続部分なら主張が依存する実DBの動作を確かめる必要がある。
`Ok` を返す代替実装で確かめられるのは、選んだ結果に対する呼び出し側の反応まで。
カバレッジは実行したコードを示すが、アサーションが関係する誤動作を拒否できるかは別になる。
リファクタリングでは外から見て必要な動作を保ち、順序が要件でなければモックの内部呼び出し順を機械的に維持しない。

## 小さく変更して、残す条件を確かめる

変更の前に、外から見える入力・戻り値・エラー・入力への変更の有無を押さえる。
ループをイテレータへ変える練習なら、構文を比べるだけでなく、同じ入力で結果と失敗時の動作を確かめる。
`fold` から `try_fold` への変更など、途中終了が変わるものは単なる別表記として扱わない。

型が同じでも意味が同じとは限らない。`&str` を受け取る二つの関数でも、空白の扱いや単位が違う場合がある。
呼び出す側が必要とする動作と、内部で自由に変えられる部分を分ける。
外部から観察できる副作用があるなら、呼び出し回数・順序も確認する。
説明できない振る舞いをまとめて書き換えず、一つの仮説を確かめられる大きさに絞る。

既存コードの制限・重複・検証を外す前に、呼び出し元、テスト、コメント、利用可能な履歴を必要な範囲で読む。
見た目だけで無駄と決めない。理由が見つからなければ「不明」とし、もっともらしい背景を作らない。
仕様が変わった場合は、古い正解例やメモも見直す。過去に通ったテストだけで現在の正しさを述べない。

## トレードオフを条件と観察に落とし込む

「場合による」で止めず、利用者の必要、制約、選択肢、選んだ理由、見直す条件を示す。
たとえば、測定した負荷を満たす逐次実装は保守しやすい選択になり得る。
非同期処理の導入には、APIを高度に見せたいという理由でなく、実際の待ち時間や並行処理の問題が必要になる。

| 関心事 | Rustで確かめる問い |
|---|---|
| 性能 | 時間を使うのは構文解析、コピー、確保、ロック、クエリ、キュー待ちのどこか。代表的な入力で測ってから最適化を選ぶ |
| 運用 | 不正入力、一時的な利用不能、結果がまだ不明な状態を運用者が区別できるか |
| 互換性 | 公開型や形式の変更後も、古いクライアントや保存済みデータを扱えるか |
| 使いやすさ | エラーが対象の入力と次の行動を伝え、必要な場合には機械が区別できる情報も保つか |
| 配布・実行環境 | 対象プラットフォーム、feature、Edition、最小ツールチェーンが実際の検証対象と一致するか |

図にするのは問いに必要な関係だけにする。借用には所有関係、enumには状態遷移、外部への作用には処理順序、
依存関係には構成図が役立つ場合がある。矢印に意味を付け、「呼ぶ」「所有する」「送信する」を混同しない。
図は疑問を解くために使い、コードを確かめる代わりにはしない。

データや並行処理には[システムの境界](systems-thinking_ja.md)を使う。
ローカルのテスト成功だけでは本番対応を確かめたことにならず、Rustのメモリ安全性の説明だけでは、
データの新しさ、永続的な処理、ユーザーデータの適切な利用は分からない。

## AIの支援量を調整する

完成コードが必要な依頼にはコードを示す。学習目的なら、その後に一つの判断を本人が行える機会を選ぶ。
「答えを見ずに失敗する入力を挙げる」「借用にした理由を説明する」「別条件への修正を書く」などから、
学びたい技能に合うものを使う。本人がヒントだけを求めたときはその希望を守る。

同じAIに「正しいか」と再質問するだけでは、独立した確認にならない。
要求から決めた期待値、コンパイラの診断、実行、公式の型定義などと照合する。
確認できない部分を見える形にし、支援の量や説明例の大きさを調整する。別エージェントの起動は必須にしない。

説明を読んで納得しただけなら、自力で検証できたとは扱わない。
反対に、一度の誤答を能力不足と決めず、予測・手掛かり・観察のどこが食い違ったかを探す。
AIへの依頼を何度も書き直すだけで詰まるなら、最小入力・型・エラーへ戻って次の確認を一つ決める。
学習の場でも、無期限に悩ませたり、失敗すること自体を目的にしたりしない。

継続学習では、見慣れないリクエストを追う、APIの境界を説明する、障害を診断する、小さな変更をレビューするなど、
本人の仕事に関係する能力を選ぶ。読む、予測する、観察する、説明するという小さな一巡を、
ツールや読了した章の数より具体的な到達点にする。ツールは確認できた障害を減らせるときに紹介する。
一つの課題やAIの利用から、キャリアの予測、生産性の倍率、定着した学習を主張しない。

レビューの説明では、指摘を観察可能な影響と実行できる変更へつなぐ。
見慣れない書き方から著者の能力を判断しない。学習者がコンパイラ用語を暗唱せずに、
何が壊れ得るか、提案した変更がなぜ役立つかを他者へ説明できる形にする。

## 再開に必要な情報を残す

長いやり取りの区切りには、必要な場合だけ短いメモを会話に残す。
「目的、使った前提、確認できたこと、まだ分からないこと、次の確認」を優先し、全ログを繰り返さない。
残す判断には理由と見直す条件を付ける。

コード調査を中断する場合は、関数や位置、現在の仮説、次に観察することと期待する結果を残す。
試したコマンドをすべて並べず、その作業を再開するのに必要な範囲へ絞る。

例：「呼び出し元が文字列を再利用するので `&str` を選んだ。移動によるエラーは再現済み。
借用後も読める理由は説明できたが、関数内で保存する設計はまだ扱っていない。次は所有が必要な場合と比べる」。

試して失敗した案は、どの条件で失敗したかを残す。「`clone()` は禁止」のように一般化しない。
新しい例で前提が変わったらメモを更新し、古い助言や重複を減らす。
説明済み・支援ありで正答・自力で確認を区別し、学習履歴の保存はユーザーが求めた場合に限る。
