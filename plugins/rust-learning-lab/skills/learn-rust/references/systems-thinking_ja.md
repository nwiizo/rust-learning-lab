# システムの境界を越えてRustを読む

[English](systems-thinking.md) | 日本語

Rustのサービス、永続化、並行する状態更新、再試行、非同期処理、型だけでは分からない性質を扱うときに使う。
関係する境界を選び、構文の質問を分散システム全体の講義へ広げない。
ここで扱うのはRustへ応用する設計上の観点であり、言語が追加で保証する性質ではない。

## 保証が及ぶ境界を特定する

説明している性質が、どの値、プロセス、保存操作、期間に及ぶかを確認する。

| Rustの記述から分かること | 支えられる判断 | 別の根拠が必要なこと |
|---|---|---|
| `&mut Client` | Rustの別名参照の規則に従い、その借用を通して排他的にアクセスする | 別のクライアント・プロセス・レプリカ経由でもDBの行を排他的に操作できるか |
| `Arc<Mutex<State>>` | 所有権を共有し、同じmutexを使うアクセスを排他する | 複数段階の処理全体の原子性、デッドロックの不在、待ち時間の上限、マシン間の協調 |
| `Send` / `Sync` | 実装が健全である前提で、スレッド間での移動／参照の共有を安全に行える | 業務上の不変条件、トランザクションの分離性、外部への作用の順序、処理がいつか完了すること |
| `Result<Receipt, Error>` と `?` | 成功・エラーの経路を表し、外側の関数などへ伝える | エラーを受け取る前に外部の操作が確定したか、それ以前の作用が取り消されたか |
| ガードと `Drop` | 破棄が実行されたとき、その型に定められた後処理を行う | 外部でのロールバック成功、永続化されたコミット、プロセス終了後の後処理、後処理のエラー通知 |

スレッドに関する厳密な性質は標準ライブラリの
[Send](https://doc.rust-lang.org/std/marker/trait.Send.html)と
[Sync](https://doc.rust-lang.org/std/marker/trait.Sync.html)で確認する。
`Arc` が任意の中身をスレッドセーフにするわけではない。
[Drop](https://doc.rust-lang.org/std/ops/trait.Drop.html)は破棄を扱い、一般的なトランザクション機構ではない。

不変条件とは、「一つの枠に有効な予約は最大一件」のように、保たなければならない条件をいう。
まず条件を明示し、それを書き換えるすべての経路を覆う仕組みを特定する。
safe Rustで書いた二つのプロセスでも、両方が「空き」を読み、予約を試みることはある。
各プロセス内部のmutexでは両者を調整できない。DBの一意性制約、原子的な条件付き更新、適切な
トランザクションなどを、実際の条件とDBの動作に合わせて選ぶ。クライアント側のRustの記号だけから決めない。

`begin()` やトランザクション型の名前から分離レベルを推定しない。たとえばPostgreSQLは、
[分離レベル](https://www.postgresql.org/docs/current/transaction-iso.html)によって防ぐ異常が異なる。
直列化の競合で再試行する場合、以前の読み取り結果を使って最後の書き込みだけをやり直すのではなく、
トランザクション内の判断全体をやり直す。DBのコミットにメール送信や別サービスの操作が自動で含まれるわけではない。

## 結果の不明を、一般的な失敗にまとめない

外部サービスにジョブを登録する場合、呼び出し側が観察したことと相手側の状態は一致しないことがある。

| 観察したこと | 相手側であり得る状態 | 次に判断すること |
|---|---|---|
| 送信前のローカル検証で拒否された | この試行からの登録はない | 入力を修正する |
| サービスがプロトコルに従って明示的に拒否した | 応答が示す条件で拒否された | 拒否理由を伝え、再試行で変わる条件があるか確認する |
| 仕様上の完了通知を受け取った | その通知が約束する範囲で完了した | 通知と、その意味する範囲を保つ |
| 送信後にタイムアウト・切断した | 未到達、処理中、完了済みのいずれもあり得る | リクエストの識別子で状態を確認するか、安全な再試行の仕組みを使う |

エラー型に `Rejected` と `OutcomeUnknown` を分ける設計も考えられる。
これはAPIの設計判断であり、すべてのRustのエラーにこのvariantが必要という規則ではない。
型を増やす前に、呼び出し側がなぜ区別を必要とするかを説明する。
復旧に必要な情報を `?` で伝播する過程で失わない。
[副作用の例](worked-examples_ja.md#エラーを返しても実行済みの作用は取り消されない)では、
まずローカルな事実として、`Err` を返しても実行済みの変更が戻らないことを確かめる。

冪等性とは、操作を繰り返しても、意図する効果が一度の実行と同じになる性質をいう。
一つのリクエスト値の所有権や `FnOnce` という境界条件では、再試行・デシリアライズ・再起動をまたぐ
この性質を保証できない。冪等性キーは受信側がそれを守る仕組みと組み合わせて初めて役立つ。
同じ論理的な操作では同じキーを保ち、同じキーに異なる内容が来た場合の拒否方法や保持期間を決める。
重複排除の記録と状態変更が別々に確定し得るなら、その間で停止した場合を確認する。
メモリ内の `HashSet` による説明例では、永続的な重複排除を検証したことにはならない。
[冪等性と再試行の設計](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)も参照する。

DBの変更と送信予定のイベントを同じトランザクションで保存する
[outbox方式](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)は、その二つの書き込みの
間に生じる隙間を埋める選択肢になる。ただし配送する処理や、受信側での重複への対応は引き続き必要になる。
すべてのアプリケーションに必須の方式でも、自動でexactly-onceになるという説明でもない。
この言葉を使う前に、「どの境界で一度なのか、どの障害を想定するのか」を確認する。

## 中断・順序・負荷を追う

### キャンセルと未完了の作業

中断し得る `.await` では、すでに何を変更したか、futureが何を保持しているか、何が未完了かを調べる。
futureのキャンセルでローカルのガードが解放されても、外部へ行った作用は残り得る。
操作のキャンセル時の動作と復旧方法を調べ、メモリ安全であることだけから、途中の進捗を捨ててよいとは判断しない。

待っているfutureが、別の処理のハンドルである場合もある。Tokioの
[JoinHandle](https://docs.rs/tokio/latest/tokio/task/struct.JoinHandle.html)をdropするとタスクは切り離され、
そのタスク自体はキャンセルされない。したがって、所有したハンドルをtimeoutで囲む場合と、
処理自体を囲む場合は同じではない。ローカルの処理をabortしても、相手が受理したリクエストは巻き戻らない。
この違いを説明するためだけにランタイムの依存関係を追加しない。

終了処理では、新しい作業の受け付けを止めること、受理済みの作業を完了または永続的に記録すること、
完了を伝えることを区別する。`Drop` だけでは非同期処理がすべて終わった証拠にならない。
`?` による早期リターンでも、中断地点でのキャンセルでも、外から観察できる状態が何かを確かめる。

### 時間と見える状態

ローカルの経過時間や締め切りには
[Instant](https://doc.rust-lang.org/std/time/struct.Instant.html)を使う。
これはマシン間で共有するタイムスタンプや、保存して順序を付ける仕組みではない。
実時間のタイムスタンプも因果関係の証拠にはならない。必要に応じて、イベント発生時刻、受信時刻、処理時刻を分ける。

書き込みに成功した後でも、遅延したレプリカやキャッシュから読むと古い値が返ることがある。
`&T` は有効な値へのアクセスを保つが、その値を最新にはしない。APIがバージョンを公開しているなら、
条件付き書き込みや仕様に定めた読み取り方針がそれをどう使うか説明する。
`Version(u64)` で包むだけでは一貫性を保つ仕組みにならない。
同様に、列の順序が保たれる範囲は、一つのパーティション内など、仕様で決まる。
複数のパーティションや並行するコンシューマーが、全体で一つの実行順序を持つとは限らない。

直列化可能性は、トランザクションが何らかの直列実行と同じ結果になる性質。
線形化可能性は、操作が実時間上の前後関係にも従う性質として区別する。
ローカルのロック、論理時刻、生成したIDだけでは、分散サービスがどちらかを提供する証拠にならない。
具体的なAPIでの範囲や例外は、[etcdの操作とwatchの区別](https://etcd.io/docs/v3.6/learning/api_guarantees/)のように、
そのAPI自体の説明で確認する。

### バックプレッシャーと費用

容量制限のあるキューは、その中に蓄える量を制限するが、満杯のときの方針も必要になる。
Tokioの[チャネルの解説](https://tokio.rs/tokio/tutorial/channels)では空きを待つ動作を説明している。
拒否、待機、破棄ではユーザーへの影響が異なる。容量はメッセージ数を制限しても、必ずしもバイト数を制限しない。
送信待ちのタスクを無制限に作れば、キューの外で大量のリクエスト本体を保持する可能性がある。

データ量、同時リクエスト数、アクセスが集中するキー、遅い依存先など、実際の負荷条件を測る。
処理そのものの時間とキューで待つ時間を分ける。p50・p95・p99などの分布は負荷とエラー率も添えて読む。
平均だけが速い場合や成功したリクエストだけの計測では、過負荷を見落とすことがある。
再試行は余力の少ないときに負荷を増やし得るため、回数や期限を受け付け制限と結び付けて考える。
再試行ループを万能の信頼性向上策としない。

## 表現と時間をまたぐデータを追う

### 必要な操作から表現を選ぶ

所有する木構造、IDで参照するグラフ、表、イベント列では、表しやすい操作が異なる。
すべての関係を入れ子の所有権へ押し込まず、循環をすべて `Rc<RefCell<_>>` で解決しようとしない。
IDはグラフの更新を扱いやすくする場合があるが、削除されたIDを検索したときの動作も決める。
`enum` は選択肢を明示し、structは同時に存在する値をまとめる。
どちらを選んでも、それだけではDB制約や通信形式は決まらない。

メモリ内のコレクションは、必要な検索、走査、順序、変更の方法から選ぶ。
`HashMap` は安定した走査順序を約束せず、`BTreeMap` はキーの順序を扱える。
どちらもDBインデックスの永続性やレプリケーションを再現するものではない。
同様に、借用したスライスでプロセス内のコピーを避けられても、ネットワークを越えるには
エンコードやバッファの所有者を決める必要がある。API全体へライフタイムや共有所有権を導入する前に、
実際にどこが費用の大半を占めるかを調べる。

### 読み取り・検証・形式の変更を分ける

バイト列をRustの型へ読み込んでも、確かめられるのはその読み取り処理が検査した条件まで。
デシリアライズした `String` が自動で有効なアカウント名になるわけではなく、`u64` だけでは単位も決まらない。
不正な値が広がるなら、検証付きコンストラクターや `TryFrom` を使う。
デシリアライズを含むすべての生成経路で条件を保つ。フィールドが非公開でも、deriveした読み取り処理が
検証用コンストラクターを呼ぶとは限らない。Serdeでは
[`try_from`](https://serde.rs/container-attrs.html)による失敗可能な変換を指定できる。

データは、それを書いた実行ファイルより長く残る。古いバイト列を新しい読み手で確認し、
段階的なデプロイやロールバックで必要なら、新しいバイト列を古い読み手でも確認する。
ワークスペース内の全呼び出し元がコンパイルできるRust APIの変更でも、保存済みデータや独立に動くクライアントを壊し得る。
[`serde(default)`](https://serde.rs/field-attrs.html)は欠けた値を補うが、その既定値の意味が適切か判断する。
[`deny_unknown_fields`](https://serde.rs/container-attrs.html)は未知のフィールドを拒否するため、
将来の追加を受け入れる方針と衝突し得る。欠落、null、明示的な既定値は自動で同じ意味にはならない。
実際の形式とバージョンごとの入力例で選択を確かめる。

### 外部への作用を繰り返さずに派生状態を作り直す

変換処理をI/Oから分けると、固定した入力を再生して出力を比べやすくなる。
イテレータの列が必ず純粋とは限らず、クロージャーが時刻、乱数、I/Oへ依存する場合もある。
結果の再現に必要な依存先、処理順序、コードとスキーマの版を特定する。
キャッシュの再構築や保存したイベントの再生で、通知まで黙って再送しない。

コンシューマーでは、出力と進捗の保存関係を確認する。進捗を先に保存すると停止後に未完了の出力を飛ばし得る。
出力を先に保存すると、再起動後に繰り返し出力し得る。両方を含むトランザクションや、
冪等な出力の仕組みがこの隙間を扱う場合がある。使う保存先によって必要な仕組みは変わり、
ローカルな `fold` がそのまま分散処理の復旧手順を備えるわけではない。

## その性質が壊れ得る層で確かめる

| 確かめたい主張 | 対応する検証 | その検証だけでは分からないこと |
|---|---|---|
| ドメインの型が不正な値を拒否する | コンストラクターのテストと、公開する全生成経路の確認 | 保存済みの全レコードの妥当性 |
| 同時に予約しても重複しない | 実DBの制約・分離レベルの下で競合するリクエストを実行する | すべての障害・復旧条件 |
| 再試行しても論理的な作用が一回になる | 応答喪失、重複、再起動を起こし、保存された結果を確認する | 再試行回数だけからの保証 |
| 形式の変更に互換性がある | 保存した新旧の入力を、必要な版の読み手で確認する | 同じ版の読み書き往復だけからの互換性 |
| 負荷が増えても利用できる | キュー、タスク、メモリ、遅い側の応答時間、拒否率、過負荷後の回復を測る | コンパイル、async構文、一つのマイクロベンチマークだけからの性能 |

モデルや制御可能な代替実装でのテストは障害を再現しやすくするが、実際の保存先の分離性・永続性の証拠にはならない。
主張が依存する境界を検証する。状態の表示では、実際に違いがあるなら「受け付け済み」と「完了」、
「失敗」と「結果をまだ確認できない」を分ける。復旧に必要な安定した情報を渡しつつ、
`Debug` やエラーログへ機密性のある本体を出さない。

データの保持期間、派生コピーの削除、認可、自動判断の理由を説明することは、プロダクト側で扱う必要がある。
所有権はRustの値のリソースを誰が管理するかを決めるが、人のデータを誰が使ってよいかは決めない。
実際のデータの流れに必要な場面で扱い、小さなRustの例すべてに本番運用の確認事項を要求しない。
