# 判断と根拠を結び付ける説明

[English](verified-explanations.md) | 日本語

Rustの詳しい解説、学習レビュー、図、章立ての教材を作るときに、必要な節を使う。
短い構文の質問には、そのまま答える。レビュー文書の保存先、参照元の版、目次については
[読み返せるレビュー文書](review-document_ja.md)に従う。

## 読者がまだ判断できない点を見つける

[学習支援の選び方](learning-design_ja.md)に沿って、質問、コード、読者自身の説明から迷っている箇所を特定する。
借用エラーを普段から直していても、参照を最後に使う位置によってコンパイル可否が変わる理由は、説明できない場合がある。
その使用箇所を指摘し、競合する理由を説明できる、といった具体的な到達点を置く。
既知と仮定することを必要な範囲で示し、足りない前提だけ補う。

コンパイラが提案する編集と、読者が実現したい動作を分ける。後の使用を削除すればコンパイルできても、
呼び出し元に必要な動作を失う場合がある。対比例では、変えた条件、コンパイラが受け入れるようになる理由、
元の課題にその変更を使えるかを説明する。比較の後は元のコードへ戻る。

## 重要な主張を、適切な確認方法へ結び付ける

実行やコンパイルの結果に依存する主張では、必要な最小例を先に確認してから観察結果を書く。
言語の規則なら、公式仕様やAPI文書を根拠に、今回のコードへの当てはめを示す。
一つの例が成功したことだけで、すべてのプログラムに成り立つ規則を証明したとはしない。

| Rustの説明で述べること | 確認に使うもの | 残すべき制限 |
|---|---|---|
| この式が原因でコンパイルできない | 対象の例、対応するツールチェーン、該当する式の診断 | ビルドは別の原因でも失敗する |
| この変更で計算結果が保たれる | 関連する入力と失敗経路に対するアサーション | 例の成功だけでは、全入力や副作用まで同等とは言えない |
| 変更操作の後でもこの参照が必要になる | ソース上の後の使用箇所と、コンパイラで確認した対比例 | 字句上のスコープを描くだけでは、借用が必要な範囲は決まらない |
| このPRで返すエラーが変わる | 対象の版と、変更前後の動作を区別できるテスト | 現在の作業ツリーのテストが、レビュー対象の版を説明するとは限らない |
| この実装は割り当てが少ない、または速い | 割り当てを確かめる根拠、または条件を示した計測 | 型や `clone()` の有無だけでは性能は決まらない |

実行結果を引用するときは、実際の出力から転記する。省略箇所を示し、診断の要約と原文を区別する。
再現に影響するコマンド、ツールチェーンの版、Edition、feature、対象の版を添える。
長い文書を検証しやすくなる場合は、「主張・確認方法・結果・制限」の表を使う。
ツールを使えない場合は予測や未実行の例として示し、出力を作らない。

適切な場合は既存のテストや `rustdoc --test --edition <edition> <document>` を使う。
`compile_fail` のdoctestはコンパイルの失敗を確認するが、それだけで意図した原因とは言えない。
診断を読み、修正した対比例がコンパイルできることも確かめる。値の確認にはアサーションを使い、
表示しただけで検証したとはしない。実行時のpanicとコンパイルエラーも区別する。
仕様は公式の[rustdocのテストガイド](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html)を参照する。

引用を繰り返し検証する方法は[ソースと出力の引用を検証する](checking-documents_ja.md)を参照する。
任意で使えるRust CLIで、ソースと出力の照合、失敗例のエラーコードと修正版の正常動作を確認できる。

## コードだけでは追いにくい問いに図を使う

描く前に、図で保つべきソースの式、登場する値、関係を短い一覧や状態表に整理する。
少数の値の変化には表、順序にはシーケンス図、依存にはグラフなど、
問いを説明しやすい形式を選ぶ。既存の描画環境を使い、小さな図ならMermaidで足りることが多い。

所有権や借用では、変数の束縛、値、参照を区別する。矢印には「所有する」「借りる」「移動する」など、
関係が分かるラベルを付ける。`String` を借用する例なら、参照の最後の使用と、所有する値の破棄を分ける。
moveを必ず物理的にデータを移す操作として描いたり、ライフタイム注釈が値の保存期間を延ばすように描いたりしない。
[Rust Bookの借用の例](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html)では、
参照を後で使う位置がなぜ重要かを確認できる。

図が表すのは、ソース上の関係、一回の実行で観察した順序、仮の経路のどれかを示す。
一回の実行記録から、並行処理で起こりうる全順序を描けたとはしない。
ラベルと矢印をソースや確認した例に対応づけ、未確認の仮定を確かな関係に見せない。

描画環境があれば、最終版を表示先の幅で見て、各矢印の行き先、ラベル、色だけに頼らない区別を確認する。
配置から誤った関係を読み取れてしまうなら、図を簡単にするか分割する。
描画できない場合は文章や表でも読めるようにし、配置は未確認と伝える。
図の構文が正しいことや見た目が整っていることだけで、意味まで正しいとは言えない。

## 長い教材は前提と判断の順で組み立てる

求められた深さと前提知識の関係に応じて章を分ける。
各章には、学ぶ判断、先に必要な知識、新たに導入する概念、関連する例を対応づける。短い構成表で足りる。
未知の概念は、導入するか既知と仮定することを示す前に、説明の前提として使わない。

借用の教材なら、所有する値と借用を渡す動作を見る、参照の最後の使用を探す、呼び出し元で値を再利用できる
関数定義を選ぶ、という順が考えられる。これは一例であり、Rustの固定カリキュラムではない。
前の説明は繰り返さず参照し、学習目的に合うなら小さな動く例から始める。

演習を求められた場合は、各目標を、学習者が示せる判断と理由へ結び付ける。
修正問題では、出発点が意図した原因で失敗し、解答が必要な動作を保って直ることを確認する。
予測や追跡の問題では動くコードが出発点でよく、失敗するテストを作るために壊さない。
解答も検証し、問題文から分けて置く。「ヒントだけ」という希望は守る。
支援の調整には[学習支援の選び方](learning-design_ja.md)を使う。

## 文書の確認と、学習の証拠を分ける

ソースとの一致、実行による確認、図の目視確認、学習者の回答を分けて報告する。
AIのレビューは前提知識の抜けや説明のつながりを見直す手がかりになるが、模擬読者の反応や想起は文書についての仮説にとどまる。
学習者が支援なしで答えた結果や、翌日の定着を測った結果として扱わない。
学習効果の主張には[研究と適用範囲](learning-evidence_ja.md)を使う。
